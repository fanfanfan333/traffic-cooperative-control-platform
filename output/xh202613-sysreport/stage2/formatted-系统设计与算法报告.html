本作品面向雄安新区"窄路密网"复杂城市肌理下的交通管控难题，构建了覆盖"仿真环境—协同算法—评估验证"全链条的车路云一体化协同管控平台，并按赛道C 要求完成 AI 交通管控模型从数据处理、模型训练、模型转换到轻量化部署验证的全流程闭环：统一 Dueling DDQN 模型同时管控 20 个形态各异的实测路口与 3 条干线走廊，平均车均延误下降 76%；模型仅 16,517 参数，经 ONNX 转换后在边缘侧纯 CPU 以 20 微秒延迟推理，1.5 万状态动作一致率 100%，满足车规级算力约束下的实时部署要求。

一、项目概述

项目以 20 个实测单路口与 3 条干线走廊为仿真对象，采用 Dueling Double DQN 深度强化学习算法实现多路口信号协同控制。核心成果包括：

  1. 一个统一模型覆盖全部 23 个场景：61 维统一状态空间（含邻居相位上下文），同一套网络参数同时部署到 20 个形态各异的单路口与 3 条干线，20 路口平均车均延误由 19.33s 降至 4.58s（下降 76%），干线延误下降 92%~94%；
  2. 完整的模型轻量化部署验证链路：PyTorch 训练模型经 ONNX 转换（FP32/FP16/INT8 三档），在 1.5 万个测试状态上验证动作一致率 100%，边缘侧单样本推理仅 20 微秒，并在仿真链路中完成部署一致性回归（PyTorch 与 ONNX 车均延误均为 4.82s）；
  3. 真实数据驱动的高保真仿真环境：场景源自雄安新区典型片区实测交通调查数据，13/20 为异形路口，如实复现"窄路密网"高密度异形交叉口特征；
  4. 企业级集成管控平台：九大功能模块、17 个 REST 接口、Docker 容器化部署，纯 CPU 可运行。

二、需求理解与总体方案

本章从赛题需求出发，给出平台的总体技术方案与"端-边-云"系统架构。

2.1 需求分析

赛题要求面向雄安新区"城市大脑"，攻克三个工程技术需求：高保真可编程仿真场景生成工具、"云-边-端"异构协同的轻量化决策算法框架、服务标准制定的性能量化评估与基准测试体系。赛道C 进一步要求完成 AI 模型"数据处理—模型训练/选择—模型转换—模型部署"全过程。

"窄路密网"片区的管控难点在于：路口间距短、异形交叉口（T 字/多进口/斜交）占比高、车流相互作用强，传统单点定时控制无法应对；而纯云端集中控制面临通信延迟与单点故障风险，纯分布式车端决策又无法保障全局最优。

2.2 总体架构：端-边-云三层协同

平台采用"端-边-云"三层架构，与车路云一体化主题严格对应：

  • 端（感知层）：SUMO/TraCI 逐秒采样车辆轨迹、车道排队、信号相位与瞬时油耗；视频管线提供 YOLOv8n 目标检测 + DeepSORT 多目标追踪的真实感知链路；
  • 边（边缘协同层）：路侧单元（RSU）承担数据聚合与模型推理——边缘节点对进口道排队做几何归并、在线检测停车事件、积分油耗；AI 模型以 ONNX Runtime 在边缘侧纯 CPU 推理，单次决策 20 微秒，完全满足 10~60 秒决策周期的实时性约束；
  • 云（决策与展示层）：承担模型训练（Dueling DDQN 离线训练与断点续训）、性能评估、标准化报告生成与实时可视化看板。

三、仿真环境构建方法

3.1 真实数据溯源

仿真场景不是理想化的"玩具路网"，而是源自雄安新区典型片区的实测交通调查数据（团队数据V2），数据链路完整可审计：

数据经过三方核对：高德地图逐路口人工核对（20/20 一致）；比赛方老师确认修正（路口13 删除违规左转相位、路口16 流量笔误 551→51、路口12 周期按相位合计修正）；质量审计确认 480 条交通流记录零重复、零需核查缺失。

3.3 扰动注入

平台"路网管理"模块支持一键注入需求扰动，用于测试非标工况下的算法鲁棒性：早高峰 ×1.5、平峰 ×0.7、突发事件 ×1.4、随机场景，对应赛题"施工占道、大型活动等扰动事件"要求。

3.4 数据集缺陷诊断（平台验证能力的佐证）

  数据集自带的 coord 协调信号程序存在缺陷：12 字符状态串套用在 11 连接路口上，导致走廊方向永无绿灯、0/800 辆车完成。平台采集器中以 --program 0 切回内置程序作为基线。该缺陷的发现与诊断过程本身即是仿真平台验证能力的直接证明。

四、协同管控算法设计

本章阐述协同管控算法的选型理由、状态/动作/奖励空间设计与训练稳定机制。

4.1 算法选型与设计思路

赛道C 的核心约束是"轻量化部署"——模型必须能在车规级芯片算力与通信带宽约束下运行。据此选择 Dueling Double DQN 而非更大的多智能体方案：

  • 推理成本极低：单次决策仅需一次前向传播，网络仅 16,517 参数，非常适合边缘部署；
  • 无通信开销：各路口共享同一策略网络、独立决策，邻居信息通过状态空间显式编码，不依赖实时多智能体通信；
  • AI 与传统控制融合：AI 只负责相位选择，交通工程硬约束（黄灯过渡、最小/最大绿灯、全红清空）在环境层兜底，保证任何决策不违反交通安全规则。

4.2 统一状态空间（61 维）

状态空间设计是"一个模型通吃所有场景"的关键：

41维单路口本体 = 4进口方向 × 3转向 × (密度/排队/速度) + 4相位one-hot + 相位时长
20维邻居上下文 = 4方向邻居槽位 × 5维邻居相位特征(单路口恒为0)

单路口与干线共享同一网络拓扑：单路口的邻居槽位恒为 0，干线路口通过邻居相位上下文"看到"上游刚放行的车队（约 36 秒后抵达），提前腾空下游绿灯——这是绿波协同在模型层面的实现机制，也是 AI 与传统绿波控制融合的具体形态。

4.3 相位语义与真实路口结构对齐

4 个动作对应真实路口的"混合放行 + 左转保护"相位结构：南北向直行左转（直行右转绿灯、左转让行绿）、南北向左转保护、东西向直行左转、东西向左转保护。该设计修复了两个历史缺陷（右转全程红灯导致延误 110s+；直左拆分导致绿灯利用率低），使原始固定配时的相位序列成为智能体策略空间的子集。消融实验证明其必要性：旧相位语义下路口1 延误卡在 20s，新语义下降至 4.75s。

4.4 网络结构与训练机制

Dueling 架构：共享特征层 FC(61→128)→ReLU→FC(128→64)→ReLU，价值流 FC(64→1) 与优势流 FC(64→4) 汇合为 Q = V + A − mean(A)。训练稳定机制包括：

机制作用
Prioritized Experience Replay高 TD 误差样本优先学习（含新样本优先级 bug 修复）
3-step 经验回放信用分配速度约 3 倍于 1-step
Huber 损失抗离群 TD 误差，大误差区间梯度有上界
学习率 warmup + 余弦退火3e-3 高学习率冷启动不发散、后期精细收敛
目标网络 Polyak 软更新τ=0.005，训练目标平滑漂移
梯度裁剪 + loss 熔断grad-norm clip 10.0，NaN/Inf 直接跳过更新

4.5 奖励函数

r = -α·tanh(ΔWait/s_d) - β·tanh(Wait/s_w) + γ·Throughput - φ·tanh(MaxLaneWait/s_w)

各项经 tanh 平滑饱和，同一套默认参数同时适配轻度/严重拥堵路口；末项为公平性惩罚，防止某方向被长期饿死；等待尺度参考值跨 episode 自动校准并按路口分别持久化，使多路口轮换训练时 reward 尺度可比。

说明：FP16 在 x86 CPU 上因无原生半精度运算单元而慢于 FP32，其价值在于具备原生 FP16 的边缘 NPU 场景（如实记录）。模型仅 16,517 参数、77.6 KB，本身就是"轻量化"的直接证据；信号控制决策周期为 10~60 秒，20 微秒的推理延迟占用决策预算不足 0.0002%，纯 CPU 即可运行，无需 GPU，满足车规级算力约束。

5.4 部署一致性回归

将 ONNX 部署模型接入仿真链路（--runtime onnx，OnnxPolicyAgent 与训练智能体接口对齐），同场景同种子 600 秒仿真回归：PyTorch 与 ONNX 车均延误均为 4.82s，41 步决策的相位选择序列逐步一致（相位分布 {0:21, 1:0, 2:20, 3:0} 完全相同）。证明边缘部署形态与云端训练模型行为等价。

5.5 端侧感知轻量化

视频管线的目标检测采用 YOLOv8n（3.2M 参数，Ultralytics 最轻量档），支持导出 ONNX 供端侧推理；ReID 模型以 ONNX 格式接入（OpenCV DNN 运行时），端-边推理链路全程不依赖训练框架。

七、系统集成与标准化价值

本章介绍企业级管控平台的功能集成、接口规范与面向地方标准的贡献点。

7.1 企业级管控平台（九大模块）

总览仪表盘（实时 KPI/趋势/资源监控）、路网管理（场景清单+雄安实测溯源+扰动注入）、GIS 地图监控（干线拓扑+路口形态标注）、协同管控算法（训练控制与曲线）、模型部署（ONNX 转换链路/精度一致性/轻量化基准/部署拓扑）、信号控制仿真（相位灯色+六维指标实时叠加，固定配时/DQN 可切）、性能评估（同种子对比+六维雷达）、云边端协同（三层实时状态）、接口文档（REST 规范+评分标准对照）。

7.2 接口规范

17 个 REST API 全部文档化（方法/路径/请求体/示例），并提供 Postman/Apifox 可导入的接口集合文件（XH-202613_platform_api.postman_collection.json），支持用 Postman/Apifox 定义并模拟测试关键数据接口，对应赛题功能一任务1 的明确要求。

7.3 标准化贡献

  1. 接口规范：端-边-云数据流与 REST 接口定义可直接作为《协同管控系统数据接口》类标准的参考；
  2. 评估体系：六维指标集（延误/时间损失/车速/通过量/等待/油耗）+ 安全维度（急刹率/二次停车率）+ 同种子可复现实验协议，符合"标准化格式的测试报告"要求；
  3. 基准测试流程：固定配时/Webster/爬山三基线 + 扰动注入工况 + 模型部署一致性验证，为地方标准中性能指标设定提供量化依据；
  4. 容器化交付：Dockerfile 一键部署，纯 CPU 可运行，降低标准验证的复现门槛。

八、结论与展望

本作品完成了面向雄安新区"城市大脑"的车路云一体化协同管控算法与仿真平台：以真实调查数据构建高保真"窄路密网"仿真环境，以统一 Dueling DDQN 模型实现 23 场景协同管控（平均延误下降 76%、干线绿波改善 92%~94%），并按赛道C 要求打通"训练—转换—量化—边缘部署"全链路，用 1.5 万状态一致性验证与部署回归证明 AI 模型可以在纯 CPU 边缘侧以 20 微秒延迟无损运行。

后续方向：将 ONNX 部署链路延伸至真实 RSU 硬件（如 Jetson 系列）实测；在状态空间中加入公交优先与应急车辆信号优先；将评估协议与接口规范整理为标准草案提交河北省智能网联汽车标准化技术委员会。
